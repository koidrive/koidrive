# 4. The server's total order

## 4.1 One commit is in flight at a time

1. The planner builds a commit (§2.6) and the engine persists it as in flight.
2. The net driver uploads the chunks the commit references (`PrepareUpload`, then `PUT` for each `UPLOAD`; spec §8 steps 1 and 2) and sends `Commit`.
3. The result updates R and S (§2.7), and the frozen nodes are released.

`base_seq` is `last_seq` when the commit is built and does not change on resend, so the server detects every change committed after it (spec §6). Only one commit is in flight (spec §8).

## 4.2 Errors and retries

| Outcome | Applied on the server? | Engine action |
|---|---|---|
| transport error, disconnect, timeout | unknown | Resend the same commit, same `commit_id`, after reconnecting and catching up |
| `MISSING_CHUNKS` | no (checked before any op, spec §8 step 4) | Upload again and resend the same commit. If the bytes are gone because the file changed since it was chunked, abandon the commit and re-plan from L with a new `commit_id` |
| `RETRY_LATER` | no | Back off for `retry_after_ms` and resend |
| `UNAUTHENTICATED` | no | Get a new access token and resend the same commit (RFC 0006 §1) |
| `INTERNAL` | unknown | Back off and resend the same commit, same `commit_id` (RFC 0006 §1) |
| `QUOTA_EXCEEDED` | no | With `retry_after_ms` above 0, back off for it and resend; without one, a policy halt |
| `READ_ONLY` (format too new, spec §9.2) | no | Abandon, stop committing, report a problem; downloads continue; queued restores end as rejected (§2.6). A `Welcome` that allows writes ends it |
| `FORBIDDEN`, `NOT_FOUND`, `CONFIRMATION_REQUIRED`, `UNSPECIFIED`, unknown code | no, or unknown | Policy halt |
| `INVALID_ARGUMENT` | no | Policy halt, keeping the commit as evidence. This is an engine bug or a reused `commit_id`, and the simulation treats it as a failure |
| `UNSUPPORTED_VERSION`, `HEAD_MOVED` | no | Abandon and re-plan with a new `commit_id` |
| `LIMIT_EXCEEDED` | no | The change records or the result do not fit in one 1 MiB message (spec §7.2). Abandon and re-plan in commits of half as many ops. A commit of one `Delete` is re-planned as deletes of the folder's contents first; a commit of one `Restore` ends that restore as not fitting; any other single op marks its node as a problem. Each acknowledged commit doubles the op count back toward 1,000 |
| `base_seq > head_seq` | no | Resync (§4.4), then re-plan |
| `HISTORY_MISMATCH` (RFC 0002 §1) | no | Stop committing; the space enters recovery as for `HISTORY_CHANGED` (§6.4), and the commit is kept as evidence |
| `STALE_DEVICE_STATE` (RFC 0002 §3) | unknown | Stop committing; recovery (§6.4) |

A policy halt (RFC 0006 §1) works as follows:

- It keeps the refused commit with its `commit_id` and slot and records the code. The engine sends nothing more to the space, neither that commit nor a new one, and downloads continue. The user sees the code and the error's message.
- The halt is stored, so it outlasts a reconnect and a restart. No `Welcome` lifts it, so it overrides the resend of §2.8.
- A `Welcome` with *w* < *a* is a loss under the halt too, handled as in §2.8 while the halt stays: *a* := *w*, the refused commit is dropped, the seqs kept for the slots above *w* are dropped, and R is listed again (§4.4). A later `Welcome` finds *w* = *a*, so the loss is handled once. A `Resend` lift after such a loss has no commit left, and its changes are planned again.
- Only a user action or a client update that knows the code ends it. Read-only differs: it follows from the device's format or role and ends with a `Welcome` that allows writes.

A commit is abandoned only after an error that proves it was not applied. An unknown outcome is resolved by the stored result, never by inference from the current tree. When it cannot be resolved, because of another history or a store older than the device's history, the space enters recovery (§6.4). Abandoning forgets the in-flight record; S was not changed for it, so the same local changes are planned again.

## 4.3 Rebase rewrites no op log

Local changes are kept as tree differences, not queued ops, so after new remote changes arrive the next commit is built from the new R, with concurrent changes resolved first (§2.4). Only two result codes rewrite a sent op, once per commit and only for the nodes named in the result: `MERGED_INTO` re-keys the folder and `CONFLICT_COPY` re-keys the file (§2.7).

## 4.4 Receiving changes

### Connecting

- After `Connected`, the engine first compares `Welcome.history_id` with R's. If they differ, the space enters recovery (§6.4) before any bootstrap or planning, so R, S and L are kept as evidence.
- Otherwise it sends `Resume{history_id, since_seq: last_seq}`, with the commit token at `last_seq` (RFC 0013), unless `last_seq` is above `head_seq` or below `log_floor_seq`; then it bootstraps with `ListTree` (spec §7.3 to §7.5).
- The engine is caught up once `last_seq` reaches the `head_seq` of the last `CaughtUp`. It builds commits only when caught up.
- An unknown change record type stops applying and committing, and the engine asks for an upgrade (spec §9.1).

### Records are applied as whole commits in seq order

- The engine applies commit `last_seq + 1`, then the next. A commit at or below `last_seq` is a duplicate and is skipped. A gap triggers a new `Resume`, and the rest of the batch is dropped.
- Within an applied commit, each `NodeState` overwrites the stored node only if its rev is above the stored one (spec §5.2), which makes the overlap between a bootstrap listing and the log replayed after it harmless. Rev gating does not allow out-of-order application: `NodePurged` has no rev, and a post-image can name a parent created by an earlier commit.
- A log replay includes the device's own commits. A result is acknowledged as §2.7 says: at once when its seq is `last_seq + 1` or already covered by R, after the gap is filled when it is further ahead. So R never gains a node whose parent is missing, and an own commit never stays in flight because its records arrived first.

### Bootstrap

After `LOG_TRUNCATED` or `AHEAD_OF_SERVER`, the engine lists the tree (spec §7.5):

- The listing is collected into a staging tree while the old R stays in use. It reads every `ListTrash` page after every `ListTree` page, merged by rev like the replay, and ends only at the `CaughtUp` sent after both (RFC 0002 §6). So a node another device trashed counts as trashed, and is never created again under an ID the server holds in its trash.
- The staging tree replaces R only after the log has been replayed up to the highest `head_seq` of any page and the result is a valid tree. Until then the planner does not run.
- Once the commit in flight was sent, the staging tree also waits for that commit's result, since the server may hold the commit. A refused resend does not end the wait, because an earlier send may have been applied. A page can hold the commit's changes without naming the commit, so only the result gives the commit's seq, which the loss rules below need. A device under a halt resends nothing, so its staging tree does not wait.
- S and L are kept, and the normal classification decides what moves in which direction, with the loss rules below.

### Commits the server lost

The server lost commits this device applied when it reports `AHEAD_OF_SERVER`, in `ResyncRequired` or by refusing a commit, or when `Welcome` reports *w* < *a* (§2.8). Each `Resume` and `Commit` names the commit token at its seq (RFC 0013), so a server whose head other devices brought back up to `last_seq` still answers `AHEAD_OF_SERVER`, instead of continuing the log over a seq it gave another commit or taking a commit built on that seq. The check claims nothing when the token is empty, as in a store upgraded from before tokens, or when its seq is 0 or below `log_floor_seq` (RFC 0013 §3), so a reused seq there passes it. The store records the loss with `last_seq` until the bootstrap replaces R, because the listing cannot show it and the device may restart in between. On the bootstrap:

- S forgets each node that the new R lacks or holds live with another shape, and every node S holds below one. A node the new R holds live with the content S holds but at another position keeps S, unless a create or move of this device that set S's position was in a lost commit. The engine records each node whose position a create or move of this device set, with that commit's seq, also when R held that position at that seq and holds it again when the result arrives. The record stays while R holds the node at that position at that revision or a later one, so another device trashing and restoring the node in place keeps it, and it counts while R holds the node in the trash there, so a loss that also takes a later delete still sends the move again. The engine also keeps the newest 64 earlier live records R held of each node, their revisions and positions, so a device that makes no commits holds a bounded history. When the seq is above the bound below, and the new R holds the node with no revision above the bound or with one of those earlier records, S takes the new R's position for the node, so the position is sent again as a move, and the nodes S holds below it keep S, so a move another device made of one of them after the loss is still taken. Where S cannot hold that position yet, because another node S holds is there, the position waits as the node's S update (§2.7) and S takes it once it fits. A lost edit of the same file takes R's content at the position that waits and waits with it, so the move and the edit are sent together once the position fits. S takes that position before the rules for lost edits and for content another device held (below) take R's content at the position S holds, so a file whose move and edit the server both lost is sent again as a move and an edit of the same file, rather than kept as a conflict copy beside the restored file, which would stay at its old position with its old content (GUN-643). A post-loss commit gets a seq the lost commits may have had, but it matches an earlier record only by setting the same position. Such a commit is usually another device sending its own lost move again, and this device's later lost move then follows it, as it did before the loss. A user who sets that same position by hand at that same seq after the loss is taken for the same record, so this device's later lost move undoes that rename. Telling the two apart needs the protocol to mark a commit that sends a lost one again (GUN-549). Otherwise R's position is taken as a remote move: another device moved the node after the loss, or a device that did not set S's position cannot tell whether a lost commit set it, and sending it again would undo that move (GUN-531). Once the engine keeps the full 1,000 slots, it forgets earlier records below the oldest one, except the newest of them, which the commit in that slot may have replaced: a later loss that keeps any slot puts the bound at or above it, and a loss of every slot leaves the bound unknown, as for a lost delete. A store from before these records starts with one for each node R holds live at a revision that is the seq of one of this device's acknowledged commits. Since it holds no earlier records, it sends such a move again whenever its commit was lost and the new R holds the node at a lower revision: every record the restored server kept is below the lost commit's seq. A node L still holds is created again rather than taken for a remote delete, and a file whose content differs from R's is kept as a conflict copy (§2.4) rather than replaced by older content.
- A node keeps S whatever the new R's shape when the old R's record of it, live or in the trash, survived: the new R holds it at the same version, or the record's content revision is at or below the bound below. S's content came from that record or an earlier one, so the server kept it, and what the new R holds otherwise is a remote change this device has not taken yet.
- A file whose content L and S held alike, with no waiting update (§2.7) to other content, while R held other content that no edit of this device set before the bootstrap holds an edit of another device this device had not taken yet, so L holds nothing the server lacks. When the new R holds the file, live or in the trash, S keeps its content and the file is never recorded as holding an unsent edit: whatever content R holds now, and a delete made before or after the loss, is a remote change. S keeps its position too, so a move R holds is a remote change, except where a commit of this device that the server lost made the old R's record of the file's position and the new R holds it live with no revision above the bound: S takes R's position, so L's position is sent again, also when that commit was the device's first. Below a folder S forgets, S forgets the file too and gets that shape back as a waiting update (§2.7) once the folder is in S again, so L's older content is not kept beside R's as a conflict copy (GUN-591).
- A node that L and S held alike while R held it in the trash holds a delete of another device that this device had not taken yet, so L holds nothing the server lacks. S keeps the node whatever the new R holds: the trash, the node missing, or content a restore brought back is a remote change, so the delete is not undone.
- A node in R's trash keeps S and stays a remote delete, also below a node S forgets. The exception is a file whose edit was lost (below): S forgets its folder only once the delete has taken what the folder held, through a waiting update (§2.7) that the effects never take for a remote delete, and the folder is then created again.
- Each waiting update records the slot of the commit whose result made it. An update from a slot above *w* is dropped, so S keeps what it held: when R holds the node as S does, the change is sent again, and otherwise S forgets the node. An update from a slot at or below *w* stays, so a change another device made since is a remote change once the update fits. An update no commit made, such as a Discard's, stays too. These rules hold for a node in R's trash as well. An effect that makes an update wait again keeps the update's slot.
- A position L and R agreed on while the commit was out (§2.7) is kept only where the restored server still holds the record that showed it: a record at or below the bound below, or one where the new R holds the node live at that position and revision. Any other agreement is dropped and taken again from L and the new R.

The bound is the seq of the newest commit of this device that the server still counts. The engine keeps the seq of each of its last 1,000 acknowledged commits by slot, and slot *w* is a commit the restored server holds, so every seq at or below its seq is from before the loss.

The commit's own record counts as its result for these records. When the record of the commit in flight arrives before its result, the commit's slot takes the record's seq, and the nodes the record shows the commit trashed, edited or positioned are recorded as above. So a loss that drops the commit before its result reaches the device sends its changes again as this device's own, rather than taking them for another device's change. S takes the content of each file the record shows the commit edited, as the result would set it. A later record in the same backlog of another device's edit of that file is then a remote change of synced content, not a conflict with this device's own write.

A delete this device made in a lost commit is sent again:

- The engine records each node a delete of this device trashed, with that commit's seq, for as long as R holds the node trashed by that commit.
- When the new R holds a recorded node live with the shape it was trashed with, as a record this device saw before the delete, and neither L nor S holds it, S takes R's shape, parents first, so the node is a local delete and is planned again. R's record is one this device saw when it has no revision above the bound, or when it is one of the earlier live records R held of the node, at that meta revision and position, and for a file also at the content revision, edit revision and version that the trashed record kept. So a node another device created, moved or edited after the bound, which this device saw and deleted, is deleted again (GUN-643). A restore from the trash keeps the version but gives the node a new meta revision, and an author's edit after another device's resend keeps the version but moves the edit revision (RFC 0018), so neither is taken for a record this device saw. A commit after the loss can take the seq a lost one had, so a trash and a restore from it after the loss that end at the very meta revision of an earlier record are taken for that record, and the delete undoes that restore. Telling the two apart needs the protocol to mark a commit that sends a lost one again (GUN-549).
- Otherwise the node is downloaded: another device changed it, a person restored it, or the bound is unknown. The delete never removes what the deleting user did not see. The keep rule of §2.4 and the server's R7 cover changes made after the listing.

An edit this device made in a lost commit is sent again:

- The engine records each file whose content an edit of this device set, at R's edit revision once R holds that content live, for as long as R holds the file live at that edit revision. When the server took the same content from another device first, that revision is the other device's. An edit in the commit in flight when the server reports the loss counts as lost too: the server holds none of that commit, and its result, which would make the record, never arrives. When the device learns of the loss, the store records the files that commit edits, with the loss. At the bootstrap each of them whose content in L still differs from S's counts as a lost edit, and the record is cleared, so an edit the user undid before the bootstrap is not sent again.
- When the new R holds such a file, live or trashed, with content of no revision above the bound or at a version the log replaced for it (below), S takes R's content at the position S holds. L's content is then a local edit and is sent again, not kept as a conflict copy, and a position R holds otherwise is a remote move. The content shows the edit was lost wherever the file is, so a move the server lost with it, this device's or another's, does not turn the edit into a conflict copy.
- A delete R holds then trashed the content from before the edit, so the edit beats it (R8): the server revives the file, and the edit does not go to the local trash. A device that downloaded the edit before the loss and deleted the file after it, or deleted the file and the conflict copy holding the edit, has its delete undone this way.

An edit back to the bytes the restore rolled the file back to is recorded so it is not lost:

- When L holds the bytes the new R holds for a file, and either S held other content or this device's edit of the file was in a lost commit, the store records the file as holding an edit the server does not have.
- A file the new R holds in the trash keeps S, so it is recorded when L holds content S does not. Any edit L makes later while R still holds the file in the trash is recorded too.
- While the record stands, the file counts as changed locally even where S and R hold the same bytes. The edit is sent as an `UpdateContent`, which gives the file a new version and content revision even for the same bytes, so the author's resend meets an edit it did not see and becomes a conflict copy (§2.4). A remote edit that arrives first makes a concurrent edit, and the edit is kept as a new file beside it (R3).
- The record ends when the server acknowledges an edit or create of the file with the content L then holds, so an edit made while an earlier one was being sent stays recorded, or when L no longer holds the file. Further local edits keep it, and so does another device removing the file: the edit beats the removal, and the file is created again.

Another device that held the lost content sends it again when it can show the restored content is older than its own:

- The engine records, per file, the version IDs R held before its current one as the log moved R forward, the newest 64. A listing records none and keeps only the recorded IDs up to the one it lists. A server never gives one version ID to two versions, also across a loss, and restoring a version makes a new one (RFC 0016).
- When the new R holds a file live at the position S holds, at a recorded version, and L and S held R's content before the bootstrap, live or in the trash, S takes R's shape and L's content is sent again as an edit. Any other content may be an edit another device made after the loss, and the file is kept as a conflict copy.
- When the author's resend and this one both reach the server, the second meets unseen content equal to its own, so neither leaves a copy (RFC 0016). If this one lands second, it changes nothing. If the author's lands second, it records an edit revision (below). A device whose user edited the file to the restored bytes after the loss records that edit as above, and so does a device that holds this resend when its user changes the file, which ends the resend. The record then stands through later edits, so an edit back to S's bytes, also after an edit to other bytes or a rename, still reaches the server before the author's resend can replace it.
- A log record that gives R the bytes S holds, while L holds a change, is a remote edit the bytes cannot show. S forgets the file, so L's change is kept beside R's as a conflict copy.

A delete made after the loss beats a resend that holds no change of this device's user (the content resend above, or the create or move of a node S forgot that L holds as S did):

- The engine records each such node, unless a commit of its own that the server lost set R's content of it, until the server takes the resend, S takes L's shape, or L changes the node. When R holds the node, or a folder L holds it under, trashed before then, S takes L's shape and the file's unsent-edit record ends, so the delete reaches L. A lost move of this device leaves the content another device's. When the restore also took that content, the node is recorded as a content resend, and a delete made after the loss beats the move with it. When the server kept the content and lost only the move, only the move is sent again. It is a change of this device's user, so it beats a delete (R8).
- A resend folder that L holds a change of this device's user under (a node created or moved into it, or an edit below it) keeps its resend. The change beats the delete (R8) and needs the folder, as it would without the loss: the server revives the deleted folders the resend goes into. The folder gives way at the next commit build once L holds no such change. A change the scan finds after the folder gave way sends the folder again at the next build, and so does one below any folder S holds and R lacks. A node S holds and R lacks that L itself changes, such as a file moved or renamed after its folder gave way, is created again at L's position. Resends give way parents first, so S takes each folder before what it holds.
- A change is a node the engine recorded as changed by this device's user that L holds as a local or concurrent change against S. The record (`local_changes`) holds a node when a scan finds L's shape changed, when a rekey copies such a change, when L holds a shape other than the one the server took from a commit of this device, or when a commit of this device that the server lost made it. It drops the node once S takes L's shape, when a scan finds L back at the shape S holds while no update of S waits, when L, S and R hold the same shape, or when L no longer holds it. An unsent edit counts as well. A node S forgot that L holds as S did is in no record, so a gap in resend marking cannot keep a folder.
- Another device sending the node again first ends a resend too. When a record or a later listing gives R the node live with the content L holds, where R lacked the node or held other content, S takes L's shape, so R's position is a remote move, as when the bootstrap's listing holds the node there.
- A commit that carries such a resend sets `require_head` (RFC 0002 §4), so a delete the server takes first refuses it with `HEAD_MOVED`, also when the commit was built before the delete reached this device. The device plans again once R holds the delete.
- A content resend carries `resend` on its `UpdateContent` (RFC 0018). The author's send of its own lost edit never does.
- Each node has an edit revision, `NodeState.edit_rev`: the seq of the newest commit that created it, changed its content other than by a resend, or carried a user's edit of content a resend brought. A resend moves `content_rev` and leaves the edit revision. An `edit_rev` of 0, from a server before RFC 0018, reads as `content_rev`.
- R7 reads the edit revision, so a delete the server takes after the resend, built without it, trashes the file. A resend whose file is trashed is answered with `SUPERSEDED`.
- The author's edit still beats such a delete. When another device's resend landed first, the author's equal send makes no version and moves no `content_rev`, but records an edit revision and revives a file a delete trashed (R8).
- A device whose user deleted the file before the resend's log record arrived plans the delete against it. When the record, of another device's commit, moves only `content_rev` and S held R's shape before it, S takes the record's shape, so the delete goes out with a base past the resend. A later record of another device's commit that moves the edit revision is the author's edit when it keeps `content_rev`, or when R held content a resend brought: an author that saw the resend before it sent its edit makes a new version with the same bytes. S forgets the file, and it is downloaded again.

`HISTORY_CHANGED`, a rewind or a point-in-time restore, starts the recovery of §6.4 instead.

## 4.5 Clients never merge each other's ops

The Space DO is a sequencer and validator, and clients are replicas of its state machine. Clients keep no vector clocks and do not converge without the server. The conflict rules are not commutative, since which side keeps a name depends on which commit came first (R1, R3), so a client never resolves an unseen conflict itself. An offline device keeps its changes as differences between L and S, rebases them and commits them when it reconnects.
